SUPERVISOR ARCHITECTURE
Agent Protocol, Wrapper Proxy, Category-Based Deployment, Telemetry
=====================================================================


OVERVIEW
--------

The supervisor is a Rust-based daemon that runs inside every Firecracker VM.
It has five roles:

1. MONITOR — watches the agent and memory binaries, restarts them if they crash
2. MCP SERVER — exposes tools to the agent so it can store/fetch tenant data
3. PROXY — forwards agent data requests to the wrapper, which owns the databases
4. DEPLOYMENT AGENT — receives plugins, configs, files, and commands from the
   wrapper based on the tenant's category
5. TELEMETRY — tracks every event, error, and latency inside the VM, writes
   daily JSON files locally, and forwards telemetry to the wrapper

The supervisor does NOT own any data. It is a protocol layer. When the agent
asks to save a memory, the supervisor asks the wrapper to save it. The wrapper
validates the tenant ID, opens the correct tenant DB, and performs the write.
Telemetry is collected locally and also forwarded to the wrapper for central
monitoring.


COMMUNICATION FLOW
------------------

[Browser/Client]
       |
       | (websocket through wrapper proxy)
       v
[Wrapper] ──────────────────────────────────────────┐
       |                                              |
       | (agent protocol over virtio-net)             | (data request + deployment)
       v                                              |
[Supervisor inside VM] ──────────────────────────────┘
       |
       | (local IPC — unix socket or shared memory)
       v
[Agent inside VM]

Flow when agent wants to save memory:
  1. Agent calls supervisor tool: save_memory(key, value, category)
  2. Supervisor packages request with tenant_id
  3. Supervisor sends to wrapper over network
  4. Wrapper validates tenant_id matches this VM
  5. Wrapper writes to tenant DB
  6. Wrapper sends response back to supervisor
  7. Supervisor returns result to agent

The agent never talks to the wrapper directly. The supervisor is the gateway.

Config:
  [telemetry]
  enabled = true
  output = "both"                    # "disk", "forward", "both", "none"

  [telemetry.disk]
  path = "/var/log/supervisor/telemetry"
  filename_pattern = "telemetry_{date}.json"
  buffer_size = 500
  flush_interval_seconds = 5
  retention_days = 7                 # shorter retention inside VM

  [telemetry.forward]
  wrapper_address = "172.16.0.1"
  wrapper_port = 9090
  batch_size = 50
  flush_interval_seconds = 10
  retry_attempts = 3
  compress = true

================================================================================
HOW THE AGENT TALKS TO THE SUPERVISOR
================================================================================

The supervisor exposes an MCP-compatible server inside the VM on a Unix
socket at /tmp/supervisor.sock.

Agent connects and calls tools:

  Agent → supervisor: {
    "jsonrpc": "2.0",
    "method": "tools/call",
    "params": {
      "name": "save_memory",
      "arguments": {
        "key": "favorite_color",
        "value": "blue",
        "category": "preference",
        "importance": 0.8
      }
    }
  }

  Supervisor → wrapper: {
    "type": "db_write",
    "tenant_id": "abc-123",
    "operation": "memory.insert",
    "data": {
      "key": "favorite_color",
      "value": "blue",
      "category": "preference",
      "importance": 0.8
    }
  }

  Wrapper → supervisor: {
    "status": "ok",
    "data": { "id": "mem_001" }
  }

  Supervisor → agent: {
    "jsonrpc": "2.0",
    "result": {
      "content": [{ "type": "text", "text": "Memory saved" }]
    }
  }


================================================================================
CATEGORY-BASED DEPLOYMENT TO SUPERVISOR
================================================================================

When a tenant is assigned to a category, the wrapper pushes a deployment
package to the supervisor. The supervisor receives and installs everything.

Deployment package from wrapper:

  {
    "tenant_id": "abc-123",
    "category": "robotics",
    "artifacts": [
      {
        "type": "supervisor_plugin",
        "name": "robotics_monitor.so",
        "path": "/usr/local/lib/supervisor/plugins/robotics_monitor.so",
        "checksum": "sha256:abc123..."
      },
      {
        "type": "agent_plugin",
        "name": "robotics_guide.so",
        "path": "/usr/local/lib/agent/plugins/robotics_guide.so",
        "checksum": "sha256:def456..."
      },
      {
        "type": "config",
        "name": "agent_robotics.conf",
        "path": "/etc/agent/agent.conf",
        "checksum": "sha256:ghi789..."
      },
      {
        "type": "binary",
        "name": "simulator",
        "path": "/usr/local/bin/simulator",
        "checksum": "sha256:jkl012..."
      },
      {
        "type": "command",
        "name": "initialize_ros.sh",
        "path": "/tmp/init.sh",
        "run_after_install": true,
        "checksum": "sha256:mno345..."
      }
    ]
  }

Supervisor processes each artifact:
  1. Verify checksum
  2. Place file at correct path
  3. Set permissions (binaries get +x)
  4. Install supervisor plugins via plugin_host (hot-reload)
  5. Execute run_after_install commands
  6. Report success/failure back to wrapper

If anything fails, supervisor reports failure and rolls back to previous state.

================================================================================
STARTUP FLOW
================================================================================

1. Load config.toml
2. Initialize telemetry
3. Initialize logging
4. Connect to wrapper, authenticate with tenant_id
5. Request category-specific deployment from wrapper
6. deployment::receive() — install plugins, configs, files, run commands
7. monitor::init()              — register agent and memory binaries
8. mcp::server::start()         — start MCP server on unix socket
9. proxy::client::connect()     — establish connection to wrapper
10. heartbeat::start()           → start sending heartbeats
11. commands::listener::start()  → listen for commands from wrapper
12. plugin_host::init()          → load all plugins from plugins/
13. plugin_host::watcher::start() → watch plugins/ for changes
14. telemetry::forward::start()  → start forwarding telemetry to wrapper
15. monitor::start()            → begin watching agent and memory binaries
16. Enter event loop            → run until shutdown command
